# Add-on proposal flow model

A pure reducer that models the execution flow of one add-on proposal: Propose,
Confirm, Cancel, execute, outcome-unknown handling, receipt lookup, the add-on
hold and generation changes. It is the spec of that flow. It is a model only:
no implementation code uses it yet, and no implementation task below is done.

Code locations are for branch `feat/addons-tables` at `4721e12d5`.

Run the model: `go test -race ./pkg/addons/model/proposalflow`.
Regenerate the viewer after any change to `reduce.go` or `traces.go`:
`go generate ./pkg/addons/model/proposalflow`.

The viewer is generated by a small Go command that runs the real reducer and
embeds the result as JSON in an HTML template. The `modeling-flows-as-reducers`
skill suggests esbuild, which bundles a JavaScript reducer. This reducer is Go,
so there is nothing to bundle; the viewer replays the Go reducer at generation
time instead of copying its logic.

## States

One constructor per situation. The model is finer than the stored state: some
constructors share one durable `gateway.ProposalState` (the `Durable()` method).

| State | Durable | Why it exists |
|---|---|---|
| `Unproposed` | none | Start. A Propose that stores nothing (held, blocked, no expiry) stays here and is retryable. |
| `Refused` | none | Propose refused: undeclared tool, read tool, role too low for the derived action, stale generation. |
| `Pending` | pending | Stored, waiting for a human decision. |
| `Admitting` | pending | Confirm accepted, waiting for the admission decision. Volatile. Needed so a second Confirm and a Cancel can race it. |
| `ExecPrepared` | executing | Executing is durable, nothing was sent. A not-sent answer returns to `Pending` (finding a). |
| `ExecSent` | executing | The request may have reached the add-on. Never goes back. |
| `OutcomeUnknown` | outcome-unknown | Sent, no evidence, automatic lookups left (counter `Lookups`). Blocks writes. |
| `UnknownManual` | outcome-unknown | Automatic lookups ran out. Blocks writes. Only a lookup answer or the owner leaves it (finding c). |
| `Abandoned` | abandoned-unknown | Owner stopped waiting. No longer blocks. A late receipt still settles it. |
| `Applied` | applied | Committed receipt. Terminal. |
| `Rejected` | rejected | The add-on definitely did not apply (rejected receipt, refusal, conflict). Terminal. |
| `NotApplied` | rejected | A lookup proved the operation never commits. Terminal. New (see findings). |
| `Cancelled` | cancelled | Never ran: proposer, hold or lowered authority. Terminal. |
| `Expired` | expired | Reached expiry unconfirmed. Terminal. |
| `Stale` | rejected | Generation moved. Terminal. |
| `Dropped` | none | Abandoned outcome removed after retention. Terminal. |

The action is not stored: `Prop.Action()` derives it from `Prop.Kind` (the tool
kind), so a proposal cannot hold an action that disagrees with its tool.

## Events

`Propose`, `Confirm`, `Cancel`, `Tick`, `AdmitGranted`, `AdmitRefused`,
`SendStarted`, `NotSent`, `ApplyResult` (committed, rejected, refused,
conflict, unsettled, transport error, timeout), `LookupDue`, `ReceiptResult`
(committed, rejected, not-committed, unsettled), `OwnerResolve`, `HoldAcquired`,
`HoldReleased`, `GenerationChanged`, `AuthorityLowered`, `Restart`,
`RetentionElapsed`.

Time enters as numbers in `Now` fields. I/O results enter as events. Effects
are `Reply`, `Persist`, `Admit`, `Dispatch`, `CancelDispatch`, `CancelSend`,
`LookupReceipt` and `Alarm`.

Two events are new contracts the shell must keep:

- `SendStarted`: the runtime client says the request is on the wire. Before it,
  a failure is `NotSent` and retryable. After it, a failure is unknown.
- `CancelDispatch` then `NotSent` or `SendStarted`: a hold or a lowered
  authority never claims a cancellation it did not achieve.

## Invariants (checked by `TestInvariants`)

Safety, on every reachable state and step:

- S1 a closed proposal never changes, so it is never Applied and Cancelled.
- S2 Applied only on a committed apply or receipt answer. A dispatch is never success.
- S3 Admitting only from Pending, by the proposer, a human surface, the stored digest, before expiry, with a live role that covers the derived action.
- S4 a schema action is never admitted for a non-owner.
- S5 execution starts only from an admission for the proposal's own generation and before expiry.
- S6 at most one dispatch, only on the admission step, always after `persist:executing`.
- S7 once sent, never back to a state that can dispatch. `ExecPrepared` returns to `Pending` only on a retryable not-sent answer.
- S8 an unknown outcome comes only from a send that may have happened, or from a restart. An admission refusal or a not-sent answer never makes one (finding a).
- S9 a blocking situation is entered only by admission.
- S10 Propose stores a proposal only with a role that covers the action derived from the tool kind, whatever action the caller claimed (finding b).
- State predicates: a schema proposal is held only for an owner, every proposal has a mutating action, the lookup counter is bounded, an abandoned outcome does not block.

Liveness: from every reachable state a terminal state is reachable (reverse
reachability over the search graph). `UnknownManual` has an exit.

## Not represented

These paths exist in the code and are outside the model. Each is a candidate
for a later extension, not a failure of this one.

- Create proposals: the reservation, `admitCreate`, `settleCreates`,
  `resolveCreate` and `BackingExists` (`proposals.go:788`, `recovery.go:383`).
- Restore from a backup (`afterRestore`, `addon_state.go:311`): pending ->
  cancelled and executing -> unknown. It needs an `AddonRestored` event.
- Revision staleness: a preview refresh after a revision change. Only the
  add-on's conflict answer is modelled (`ApplyResult{conflict}`).
- Quotas, retention pressure and `makeRoom` (`proposals.go:982`).
- Cross-proposal blocking is an input (`Propose.Blocked`, `AdmitRefused{blocked}`),
  not a model of two proposals.
- The gateway's `byState` rewrite of a 503 into an unknown outcome
  (`proposals.go:1370`). It reads the stored state, so with finding (a) it turns
  a not-sent failure of an executing proposal into "unknown" for the caller.
- `Resolve` of an executing proposal after a crash and before `Recover`: the
  code allows it when no call is live; the model answers closed.
- Per-user and per-resource scope. The model has one proposal, one proposer and
  one other user.
